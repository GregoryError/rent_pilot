## Фаза 1 — сервер

Интерфейс гостя не менялся: по ссылкам `/book/{secret}`, `/widget/{secret}` и `/widget.js`
работает прежний виджет, но уже на новой серверной логике. Новый API пока никем не
используется — его потребитель появится в фазе 2.

### Выкладка

1. `git push` → автодеплой на staging. Миграция V29 применится сама.
2. Новых обязательных переменных окружения нет. Необязательные — SMTP (см. ниже).
3. После деплоя — hard reload (⌘⇧R).
4. `HCAPTCHA_SITE_KEY` / `HCAPTCHA_SECRET` из `.env` можно удалить: капча убрана.

Миграция V29 только добавляет колонки и таблицу `promo_codes`. `booking_widgets.hold_hours`
остаётся в таблице, но больше не читается — срок резерва теперь в `hold_minutes`
(заполняется из `hold_hours * 60`). Существующим виджетам выдаётся адрес `w<id>`,
поменять его можно в настройках.

### Что изменилось для хозяина

- **Настройки страницы бронирования** (`/settings/widgets/{id}`): режим «заявка / сразу
  бронь», сбор за уборку, скидки от 7 и от 28 ночей, предоплата %, «можно с питомцами»,
  дни недели без заезда и без выезда, адрес страницы, сайты для встраивания, контакты
  для гостя, промокоды.
- **Заявки** (`/bookings/pending`): подтверждённую бронь можно отменить, пока гость не
  выехал; у заявок появился номер.
- **Telegram**: за два часа до истечения заявки приходит напоминание (если резерв
  длиннее четырёх часов). В режиме «сразу бронь» приходит сообщение о новой брони.

### Эхо броней виджета

Заявки и брони виджета защищены от эха тем же механизмом, что ручные записи
(`INTEGRATION_MANUAL_ECHO.md`):

| | Ручная запись | Заявка / бронь виджета |
|---|---|---|
| UID в экспорте | `optirent-manual-<id>@optirent.ru` | `optirent-widget-<UUID заявки>@optirent.ru` |
| Событие с нашим UID во входящем фиде | не импортируется | не импортируется |
| Чужой UID, даты совпали, записи ≤ 7 дней | блокировка-тень | блокировка-тень |
| Удаление / отклонение / истечение / отмена | `cancelled_at`, 90 дней `STATUS:CANCELLED` | то же |
| Тени при удалении | без признаков настоящей брони — `ignored` | то же |

Чтобы это работало, у заявки теперь есть блок-«якорь» в `calendar_blocks` на всё время
жизни брони: `HOLD`, пока хозяин не ответил, и новый тип `WIDGET_BOOKING` после
подтверждения (раньше резерв при подтверждении удалялся). Занятость подтверждённой брони
даёт сама бронь; `AvailabilityService.withoutActiveShadows` якорь `WIDGET_BOOKING` не
считает. UID события один и тот же для резерва, брони и отмены — раньше при подтверждении
он менялся с UUID на `booking-<id>`, и площадка видела «одно событие пропало, другое
появилось».

Следствия, о которых стоит знать:

- Отклонённые и истёкшие заявки 90 дней остаются в iCal-фидах со `STATUS:CANCELLED`.
  Спам-заявки ограничены лимитом (10 в час с IP), но при всплеске фид вырастет.
  Выключатель общий с ручными записями: `APP_ICAL_EXPORT_CANCELLED=false`.
- Брони виджета, подтверждённые до V29, якоря не имеют: при отмене у них просто меняется
  статус, теней и `STATUS:CANCELLED` не будет. Их UID в фиде один раз сменится с
  `booking-<id>` на `optirent-widget-<UUID>`.

### CORS и встраивание в iframe

Раньше API виджета отвечал любому сайту, а `/widget/**` можно было вставить в iframe где
угодно. Теперь:

- Запрос с чужого сайта проходит, только если сайт указан в настройках виджета
  («Сайты, где можно разместить виджет»). Остальным — 403, включая preflight.
- Страница `/widget/{secret}` отдаёт `Content-Security-Policy: frame-ancestors 'self'
  <сайты из списка>`. Все остальные страницы — `X-Frame-Options: DENY`.
- Пустой список — виджет работает только по ссылке на нашем домене.

**Если виджет уже встроен на чей-то сайт (скриптом или iframe), после выкладки он
перестанет работать, пока сайт не добавят в список.** На staging таких вставок нет.

Проверить на staging, что nginx сам не добавляет `X-Frame-Options` и не затирает
`Content-Security-Policy` — иначе iframe не откроется и на разрешённом сайте.

### Публичный API (для фазы 2)

Ключ — адрес виджета. Без авторизации, без CSRF, лимит 60 запросов в минуту с IP.

| Метод | Адрес | Что отдаёт |
|---|---|---|
| GET | `/api/widget/{slug}/config` | настройки, тексты, раскладка |
| GET | `/api/widget/{slug}/availability?from=&to=` | дни: `d` дата, `p` цена ночи, `b` занято, `ci` / `co` — почему нельзя заехать / выехать (`busy`, `rule`, `gap`) |
| GET | `/api/widget/{slug}/alternatives?checkin=&checkout=` | до трёх ближайших свободных интервалов той же длины |
| POST | `/api/widget/{slug}/quote` | разбивка суммы и `formToken` |
| POST | `/api/widget/{slug}/booking` | заявка или бронь: номер, `requestId`, ссылка на `.ics`, контакты хозяина |
| GET | `/api/widget/{slug}/bookings/{requestId}/calendar.ics` | событие для календаря гостя |

GET-ответы: `Cache-Control: public, max-age=60` и `ETag` (повторный запрос — 304).
Серверного кэша нет: доступность считается двумя запросами по индексам, а устаревшие на
минуту данные не опасны — бронь всё равно перепроверяется под блокировкой.

Ошибки — `{code, message}`. `code` — для перевода в виджете (`DATES_TAKEN`, `MIN_NIGHTS`,
`PROMO_EXPIRED`, `PRICE_CHANGED`, `TOO_FAST`…, полный список — `WidgetError`), `message` —
русский текст. `409` — даты заняли или сумма изменилась (в ответе новый расчёт).

Сумму считает только сервер (`WidgetPricing`): ночи → скидка за длительность (от 7 и от
28 ночей, действует бо́льшая) → промокод → уборка. Клиент передаёт `expectedTotal`; если
цена изменилась, пока гость заполнял форму, бронь не создаётся.

### Защита от спама

Капчи нет. Работают: honeypot-поле, лимит 10 заявок в час с IP, проверка времени
заполнения. Сервер выдаёт подписанную отметку времени вместе с расчётом суммы и не
принимает форму раньше чем через 3 секунды (`TOO_FAST`) и позже чем через 12 часов
(`FORM_EXPIRED`). Подпись — на ключе из `ENCRYPTION_KEY`, перезапуск приложения токены не
ломает.

Старый адрес `/widget/{secret}/request` отметку времени не проверяет (прежний виджет её
не знает) — до фазы 7 это обходной путь для бота. Honeypot и лимит на нём работают.

### Гонка

Перед созданием брони блокируется строка категории (`SELECT … FOR UPDATE`) и занятость
проверяется заново в той же транзакции. Промокод блокируется так же — последнее
применение не достанется двоим.

### Письма (SMTP)

Реализация есть, по умолчанию выключена. Включается переменными в `.env`:

```
SMTP_HOST=smtp.example.ru
SMTP_PORT=465
SMTP_USERNAME=booking@optirent.ru
SMTP_PASSWORD=...
MAIL_FROM=OptiRent <booking@optirent.ru>
```

Порт 465 с SSL; для 587 со STARTTLS нужна правка `application.yml`
(`spring.mail.properties.mail.smtp.ssl.enable` → `starttls.enable`). Письмо гостю уходит
при заявке, подтверждении, отклонении и отмене — если гость оставил email. Без SMTP письма
молча пропускаются.

### Платежи — точки расширения

Оплата сейчас оффлайн: гость видит сумму предоплаты, хозяин договаривается сам.

- `payment/PaymentProvider` — интерфейс: `start(booking, prepayment)` возвращает
  `PaymentStart(kind, redirectUrl)`. Единственная реализация — `OfflinePaymentProvider`.
- `WidgetApiController.booking` уже вызывает провайдера и отдаёт виджету
  `payment: {kind, redirectUrl}`. Для онлайн-оплаты: новая реализация (`@Primary` или
  выбор по настройке виджета), `kind = REDIRECT`.
- `booking_widgets.prepayment_percent`, `bookings.prepayment_amount` уже есть.
  `bookings.amount_paid` существует с V1.
- Для оплаты понадобится режим «резерв до оплаты»: `hold_minutes = 30`, бронь `PENDING`,
  подтверждение — вебхуком провайдера через `WidgetBookingService.confirm`. Истечение
  резерва уже работает (`expireHolds`).
- Вебхук провайдера — новый публичный эндпоинт без CSRF, с проверкой подписи.

### Тесты

`mvn -o test` — 185 unit-тестов. Ещё 9 тестов в `WidgetBookingIntegrationTest` идут на
настоящем PostgreSQL в контейнере (Testcontainers) и без docker пропускаются:

- восемь одновременных заявок на одни даты — проходит одна (без `FOR UPDATE` проходят
  все восемь — проверено);
- последнее применение промокода при двух одновременных бронях;
- сквозной сценарий API: расчёт → бронь → занято → UID-маркер в iCal-фиде → подтверждение
  → отмена со `STATUS:CANCELLED`;
- CORS, ETag, `frame-ancestors`;
- страницы админки рендерятся, формы сохраняются.

Запуск с colima:

### Известные ограничения фазы 1

- **Не проверено в браузере.** Сервер проверен тестами на PostgreSQL; как выглядят новые
  поля настроек и что прежний виджет по-прежнему работает на staging — нужно посмотреть.
- **Отправка писем не проверялась** — нет SMTP-доступов. Код отправки выполняется только
  с заданными `SMTP_HOST` и `MAIL_FROM`.
- **Текст согласия.** Сервер требует флаг согласия и сохраняет его время
  (`bookings.consent_at`). Отдельного текста согласия гостя на передачу контактов хозяину
  в `legal_pages` по-прежнему нет — его нужно написать до выхода виджета к хостам.
- **Имя гостя хранится инициалом** (`PdAnonymizer`), как и раньше. В письме гостю
  обращения по имени нет.
- **Запреты по дням недели — на уровне виджета.** Минимального срока и запретов «по
  датам» в модели нет; «с этой даты минимум N ночей» вычисляется из соседних броней.
- **Категории с несколькими номерами** (`unit_count > 1`): эхо по датам для них не
  определяется (как и для ручных записей), `STATUS:CANCELLED` в их фиде не отдаётся.
- **Удаление страницы бронирования** не отменяет её заявки и брони.
- **В `widget-core.js` остался код hCaptcha** — он не выполняется (ключ сервер больше не
  отдаёт). Файл целиком заменяется в фазе 2.
- **Лимиты запросов — в памяти процесса**, обнуляются при рестарте.

## Фаза 2 — Web Component

Новый виджет — `<optirent-booking data-widget="slug">`, бандл `/w.js`. Гостям он пока не
показывается: старые ссылки по-прежнему открывают прежний виджет. Посмотреть новый —
кнопка «Новый виджет — предпросмотр» на странице настроек
(`/settings/widgets/{id}/preview`). Заявки из предпросмотра настоящие.

### Выкладка

`git push`. Миграций и переменных окружения нет. После деплоя — hard reload.

### Исходники и сборка

```
widget/
  src/          index.js (компонент), calendar.js, rules.js, dates.js, i18n.js, dom.js, styles.css
  test/         rules.test.js (node --test), host.html (страница с агрессивным CSS)
  build.mjs     esbuild → src/main/resources/static/w.js
```

```bash
cd widget
npm install      # один раз
npm test         # логика дат и правил выбора
npm run build    # пересобрать w.js
```

`w.js` лежит в репозитории собранным: docker-сборка приложения про node не знает. В первой
строке бандла — хэш исходников; `WidgetBundleTest` (`mvn test`) падает, если `w.js` собран
не из текущего `widget/src`. **Поменяли что-то в `widget/` — пересоберите и закоммитьте
`w.js` вместе с исходниками.**

Размер (gzip): JS ≈ 13,8 КБ из 35, CSS 3,2 КБ из 15. Бюджет проверяет и `build.mjs`
(отдельно JS и CSS), и `WidgetBundleTest` (суммарно).

### Что умеет

- **Изоляция.** Shadow DOM; корень сбрасывает наследуемые стили (`all: initial` плюс
  `direction`), сам элемент защищён от `display` / `float` чужой страницы.
- **Календарь диапазона.** Два месяца на широком контейнере, один на узком; цена ночи в
  ячейке; занятые дни перечёркнуты; дни, где нельзя заехать или выехать либо не хватает
  минимального срока, помечены точкой и по нажатию объясняют причину; предпросмотр
  диапазона при наведении; свайп по месяцам. Дальние месяцы догружаются при листании.
- **Узкий контейнер (< 600 px).** Календарь и гости открываются листом снизу
  (`<dialog>`: фокус-ловушка и Esc — штатные), внизу липкая панель с ценой и кнопкой.
  Ширина считается по контейнеру, а не по окну.
- **Сумма** — с сервера: ночи (с разными ценами), скидка за длительность, промокод,
  уборка, итог, предоплата. Скелетоны вместо спиннеров.
- **Занятые даты.** Если даты из ссылки заняты или их заняли, пока гость заполнял форму, —
  до трёх ближайших вариантов той же длины одним нажатием.
- **Ссылка с предзаполнением:** `?checkin=2026-11-13&checkout=2026-11-15&guests=2`
  (ещё `adults`, `children`, `pets`, `promo`); то же атрибутами `data-checkin` и т. д.
  `utm_*` и referrer уходят в бронь.
- **Экран подтверждения:** номер, даты и время, сумма, до какого времени держатся даты,
  «Добавить в календарь», контакты хозяина, правила.
- **ru / en**: по языку браузера, переключатель в шапке, `data-lang`. Цены всегда в рублях,
  формат ru-RU.
- **Доступность:** календарь — `role="grid"`, стрелки, Home / End, PageUp / PageDown,
  Enter, Esc (сначала отменяет начатый выбор, потом закрывает окно); выбранный диапазон и
  итог объявляются через `aria-live`; ошибки полей привязаны к полям.
- **Анимации** — только `transform` и `opacity`, 150–260 мс; при
  `prefers-reduced-motion` выключаются все.
- **События** `optirent:step` (`view`, `dates`, `form`, `submit`, `success`) — задел под
  аналитику фазы 6.

### Как проверялось

Локально: приложение на PostgreSQL в контейнере, виджет — на странице с другого origin
(`widget/test/host.html`: `* { all: unset }`, чужие шрифты, `direction: rtl`), headless
Chrome через скрипт. Прошли: выбор дат мышью, касанием и с клавиатуры; подсказки по
недоступным дням; расчёт со скидкой и промокодом; ошибки полей; отправка и экран
подтверждения; `.ics`; лист на 320 и 360 px; ссылка с датами (свободными и занятыми);
тёмная тема; английский. Скриншоты смотрел на ширинах 320, 360, 768, 1280.

Найдено и исправлено по ходу: поле-ловушка за краем экрана растягивало страницу с
`direction: rtl`; наследовался `direction`; фокус в календаре терялся при пересчёте
раскладки; одновременные запросы дней календаря обгоняли друг друга; повторная отправка
после `TOO_FAST` съедала лимит заявок гостя (лимит теперь считает только прошедшие
проверку формы).

### Не сделано и не проверено

- **Живой браузер и телефон.** Проверка — в headless Chrome. Safari, Firefox и настоящие
  телефоны не смотрел; `<dialog>` и container queries требуют Safari 16+.
- **60 fps и Lighthouse не мерил.** Lighthouse по условиям приёмки меряется на `/b/<slug>`
  (фаза 7).
- **View Transitions не использую.** `document.startViewTransition` делает снимок всей
  страницы хозяина — на чужом сайте это недопустимо. Смена месяца и окна — на CSS.
  На собственной странице `/b/<slug>` можно включить в фазе 7.
- **Лист не закрывается жестом вниз** — только кнопкой, крестиком, Esc и касанием фона.
- **Ячейка календаря на ширине 320 px — 44 × 46 px**, впритык к минимуму.
- **Запасной вариант без container queries** покрывает только двухколоночную раскладку.
- **Галерея, описание, карта, компоновки, выбор цвета и шрифта** — фазы 3–4. Сейчас
  раскладка одна: календарь слева, форма справа; на узком — колонкой.
- **Шрифт** — системный.
- **Текст согласия** ссылается на `/legal/privacy`; отдельного текста согласия гостя
  по-прежнему нет.

## Фаза 3 — фотографии и галерея

Хозяин загружает фото в настройках страницы бронирования (блок «Фотографии»); новый виджет
показывает их галереей. Прежний виджет и `/book/{secret}` по-прежнему берут фото из ссылок
(`photos_json`) — загруженные фото в них появятся, когда их заменит страница `/b/<slug>`.

### Выкладка

1. **nginx: поднять лимит тела запроса.** По умолчанию он 1 МБ, фото с телефона — 3–10 МБ,
   и загрузка упрётся в `413 Request Entity Too Large`. В блок `server` для staging
   (и позже prod) добавить `client_max_body_size 100m;` и `nginx -s reload`. Приложение
   принимает до 20 МБ на файл и 100 МБ на запрос.
2. `git push`. Миграция V30 создаёт `widget_photos`.
3. Образ теперь ставит `libwebp-tools` (утилита `cwebp`, +70 КБ) — первая сборка чуть дольше.
4. Том `rentoptima-staging_uploads` docker compose создаст сам при первом запуске.

Если `cwebp` в контейнере не окажется, загрузка не ломается: фото сохраняются только в
JPEG, на странице настроек об этом появится строка.

### Том с фотографиями — в бэкапы

Файлы лежат в томе, в базе — только их описания (`widget_photos`). **Том нужно бэкапить
вместе с дампом БД**: дамп без файлов даст галереи из битых картинок, файлы без дампа
бесполезны.

```bash
# вместе с pg_dump
docker run --rm -v rentoptima-staging_uploads:/data:ro -v "$PWD":/backup alpine \
    tar czf /backup/uploads-$(date +%F).tar.gz -C /data .

# восстановление
docker run --rm -v rentoptima-staging_uploads:/data -v "$PWD":/backup alpine \
    tar xzf /backup/uploads-ГГГГ-ММ-ДД.tar.gz -C /data
```

Порядок при бэкапе: сначала дамп БД, потом архив тома — тогда в архиве точно есть файлы
всех фото из дампа (лишние файлы безвредны). Для prod и partner том и переменную
`APP_UPLOADS_DIR=/data/uploads` нужно добавить в их compose-файлы на сервере
(`docker-compose.yml` в репозитории — staging). **Без тома фото пропадут при пересборке
контейнера.**

### Как устроено

- **Обработка при загрузке** (`PhotoProcessor`): поворот по EXIF, варианты шириной 480, 960
  и 1600 px (не шире оригинала) в JPEG и WebP, заглушка LQIP — JPEG 24 px в data URI,
  около 1 КБ. Оригинал не хранится.
- **Приватность.** Файлы кодируются заново из пикселей — EXIF, включая координаты съёмки,
  в них не попадает.
- **Память.** Большой снимок декодируется сразу уменьшенным; предел — 60 Мп и 20 МБ.
- **Хранение.** `<APP_UPLOADS_DIR>/widget/<32 hex>-<ширина>.<jpg|webp>`. Имя случайное, по
  нему нельзя перебрать чужие фото.
- **Отдача.** `GET /media/widget/<файл>` — без авторизации, `Cache-Control: max-age=1 год,
  immutable`. Имя проверяется по шаблону, выход из каталога невозможен.
- **Лимиты:** 12 фото на виджет, JPEG и PNG. HEIC не принимается — iPhone при выборе фото в
  браузере обычно сам отдаёт JPEG; если нет, хозяин увидит «Подойдут файлы JPEG и PNG».
- **Виджет** получает в `config.photos` готовые `srcset` для JPEG и WebP, размеры и
  заглушку. Галерея: нативная прокрутка со `scroll-snap` (свайп без JS на кадр), точки,
  счётчик «3/12», стрелки для мыши, клавиши ← →, полноэкранный просмотр в `<dialog>`.
  Место под фото занято заранее (`aspect-ratio`), первое фото грузится сразу, остальные —
  `loading="lazy"`. Ссылки из `photos_json` показываются после загруженных фото, без
  вариантов и заглушки.

### Как проверялось

- Unit: все восемь ориентаций EXIF, чтение тега в обоих порядках байт, набор ширин,
  WebP легче JPEG, работа без `cwebp`, PNG с прозрачностью, отказы, отсутствие EXIF в
  результате, проверка имён файлов, лимит и порядок.
- На PostgreSQL: загрузка через форму админки (вместе с «не фото» в том же запросе), отдача
  с кэшем, попадание в `config`, запрет удаления чужим tenant'ом.
- Локально в headless Chrome: загрузил четыре фото 3000 px через настоящую форму (4 с на
  все), посмотрел галерею на 1280 и 360 px, полноэкранный просмотр, свайп, клавиши.
  Layout shift на странице с галереей — 0. На телефонном экране с плотностью 2 браузер взял
  вариант 960 WebP. WebP на этих снимках втрое легче JPEG (45 КБ против 137 КБ при 1600 px).

### Не сделано и не проверено

- **nginx-лимит и сборка образа с `libwebp-tools` на сервере** — не проверял; `cwebp` в
  `eclipse-temurin:21-jre-alpine` ставится и работает (проверил локально в контейнере).
- **Ленивого отдельного бандла галереи нет.** Весь виджет с галереей — 14,8 КБ JS из 35;
  отдельный файл ради ~1 КБ добавил бы запрос и усложнил сборку. Лениво грузятся сами фото.
- **AVIF нет** — как договаривались.
- **Перетаскивания фото нет** — порядок кнопками ← →. Загрузка идёт обычной формой, без
  полосы прогресса; на медленном интернете несколько больших фото грузятся долго.
- **Удаление страницы бронирования не удаляет её фото** с диска.
- **Тестовые снимки — абстрактные обои macOS**, не интерьеры: на настоящих фото выигрыш
  WebP будет другим.
- **Превью ссылки в мессенджере** (`og:image`) пока берётся из ссылок, не из загруженных
  фото — это фаза 7.
