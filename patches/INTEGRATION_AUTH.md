## 1. Почта

### Что сделано

- `mail/MailConfig` — свой `JavaMailSender` вместо автоконфигурации Spring Boot. Шифрование
  задаёт `SMTP_SECURITY`:
  - `starttls` — порт 587 (и 25); `starttls.required=true`, без STARTTLS письмо не уходит;
  - `ssl` — порт 465, TLS с первого байта;
  - пусто — по порту: 465 → ssl, остальное → starttls.

  Открытого режима нет. Прежняя переменная `SMTP_SSL` больше не читается.
- `mail/Mail` + `mail/MailRenderer` — письмо как данные (заголовок, абзацы, одна кнопка,
  приписка). Из него собираются HTML (таблица со встроенными стилями, без картинок и внешних
  ресурсов) и текстовая часть; адрес кнопки повторяется текстом под ней.
- `EmailService.send(Mail)` — единственная точка отправки. У каждого письма:
  - `multipart/alternative`: `text/plain` + `text/html`, UTF-8; тема и имя отправителя
    кодируются по RFC 2047;
  - `Reply-To: MAIL_REPLY_TO` (пусто — заголовка нет);
  - `X-UNISENDER-GO: {"track_links":0,"track_read":0}` — Unisender не подменяет ссылки на
    свой адрес-переадресацию (`links.optirent.ru`) и не вставляет пиксель прочтения. Ключи —
    по godocs.unisender.ru/smtp-api; согласования поддержки они не требуют.
  - при `MAIL_SKIP_UNSUBSCRIBE=1` в заголовок добавляется `"skip_unsubscribe":1`.
- Письма гостям виджета (`WidgetNotifier`) переведены на `Mail` — тоже HTML + текст и те же
  заголовки.
- Тесты — `mail/EmailServiceTest` на GreenMail (тестовый SMTP, зависимость `test`): HTML и
  текст, кириллица, Reply-To, `X-UNISENDER-GO`, `skip_unsubscribe`, режим ssl против SMTPS,
  выбор режима по порту, экранирование, поведение без `SMTP_HOST`.

### Переменные (.env на сервере, в коде значений нет)

| Переменная | Значение на staging | Комментарий |
|---|---|---|
| `SMTP_HOST` | `smtp.go2.unisender.ru` | пусто — письма не уходят |
| `SMTP_PORT` | `587` | по умолчанию 587 |
| `SMTP_SECURITY` | — (не задавать) | `starttls` / `ssl`; пусто — по порту |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | user_id / API-ключ | |
| `MAIL_FROM` | `OptiRent <no-reply@optirent.ru>` | пусто — письма не уходят |
| `MAIL_REPLY_TO` | **добавить**: ящик, который читаете | на no-reply письма не принимаются |
| `MAIL_SKIP_UNSUBSCRIBE` | `0` | `1` — только после разрешения поддержки |

В `docker-compose.yml` всё проброшено через `${…}`; `docker compose config` проверен с
переменными и без них. STARTTLS на `smtp.go2.unisender.ru:587` проверен
`openssl s_client -starttls smtp` — сертификат валиден.

### Ссылка отписки и что делать, если пользователь отписался

Пока поддержка Unisender не включила `skip_unsubscribe`, Unisender сам дописывает в подвал
HTML-части **каждого** письма ссылку отписки — в том числе письма сброса пароля. Отдельного
статуса «отписан от рассылок, но служебные получает» у Unisender Go нет: отписка заносит адрес
в список недоступных (suppression list, `cause = unsubscribed`), и дальше письма на него не
уходят вовсе. Обойти это из письма нельзя: флаги `bypass_unsubscribed` / `bypass_global` есть
только в Web API (`email/send`), в SMTP-заголовке их нет, и `bypass_unsubscribed` тоже работает
лишь после разрешения поддержки.

Поэтому:

1. **Главное — попросить поддержку включить `skip_unsubscribe`** (или отключить ссылку
   отписки для аккаунта целиком: писем-рассылок мы не шлём, только служебные). После
   разрешения — `MAIL_SKIP_UNSUBSCRIBE=1` в `.env` и `docker compose up -d`.
2. Если пользователь уже отписался и не может сбросить пароль:
   - проверить адрес: Web API `suppression/get` (`email`, при проектах — `all_projects=true`).
     В ответе `cause` и `is_deletable`;
   - `cause = unsubscribed` и `is_deletable = true` → `suppression/delete` (`email`) — адрес
     снова получает письма. У метода дневной лимит (ошибка 906);
   - запись не удаляется (`is_deletable = false`, ошибка 3004) → `email/subscribe`: Unisender
     пришлёт человеку письмо со ссылкой повторной подписки (не чаще раза в сутки);
   - пока адрес недоступен — сброс через Telegram на `/forgot` (если у пользователя подключён
     бот) или администратор задаёт временный пароль вручную (команда — в разделе 2).
3. `complained` (человек нажал «Спам») и `blocked` (запрет администрации Unisender) — так же
   через `suppression/get`; `blocked` снимает только поддержка.

Записи списка недоступных привязаны к проекту Unisender (у записи есть `project_id`).
Если когда-нибудь появятся рассылки, их стоит слать из отдельного проекта, чтобы отписка от
рассылки не задевала служебные письма; это стоит подтвердить у поддержки.

## 2. Восстановление и смена пароля (V37)

### Что сделано

- **`auth_tokens`** (V37): одноразовые токены ссылок — `RESET` (сброс пароля) и `VERIFY`
  (подтверждение почты, фаза 3). Токен — 32 байта из `SecureRandom`, в адресе base64url
  (43 символа), в базе **только SHA-256** (`token_hash`). Время — `TIMESTAMPTZ`. Новая
  ссылка гасит прежние того же вида; гашение — одним `UPDATE … RETURNING`, поэтому дважды
  ссылку не потратить. Старые колонки `users.password_reset_token` / `email_verification_token`
  (V12, токен открытым текстом) больше не используются, значения стёрты.
- **`/forgot`** — адрес и две кнопки: «Прислать ссылку на почту» и «Прислать ссылку в Telegram».
  Ответ всегда один и тот же («Если такой адрес зарегистрирован…»): есть аккаунт или нет,
  подключён Telegram или нет, сработал лимит или нет. Письмо и сообщение уходят в фоне
  (`AuthNotifier`, `@Async`), чтобы время ответа не выдавало найденный адрес.
  - Telegram — бот тенанта (`system_settings.tg_bot_token` + `tg_chat_id`, раздел «Интеграции»).
    Колонка `users.tg_chat_id` не используется.
  - Лимиты (`PublicRateLimiter`, в памяти процесса): 3 запроса на адрес в час, 10 с IP в час;
    считаются до поиска пользователя.
  - Без SMTP: «Восстановление по почте временно недоступно», остаётся кнопка Telegram.
- **`/reset?token=…`** — GET только показывает форму (предпросмотр почты или Telegram ссылку
  не тратит), токен гасится при отправке. Требования к паролю (`PasswordPolicy`: от 10 символов,
  не совпадает с адресом почты) видны под полем сразу. Страница не кэшируется,
  `Referrer-Policy: no-referrer`. Успех — `/login?reset`.
- **После нового пароля** (сброс или смена): остальные сессии пользователя завершаются
  (`SessionRegistry`, следующий запрос из них → `/login?expired`), ссылки сброса гаснут, на почту
  уходит «Пароль OptiRent изменён — если это были не вы, ответьте на это письмо» (Reply-To —
  `MAIL_REPLY_TO`). Сброс по ссылке из письма заодно ставит `email_verified = true`.
- **«Сменить пароль»** — в блоке «Помощь» внизу меню, `/account/password`: текущий + новый дважды.
  Неверный текущий пароль — не больше 10 попыток в час.
- **Ссылки в письмах** строит `SiteSettings.linkBase`: на prod — `APP_BASE_URL`, вне prod — адрес
  запроса, если хост наш (`*.optirent.ru`, localhost); подменённый `Host` даёт ссылку на
  `https://optirent.ru`, а не на чужой сайт. Ссылка со staging ведёт на staging.
- «Забыли пароль?» на странице входа; `/forgot`, `/reset`, `/account/` закрыты в `robots.txt`;
  страницы добавлены в `tools/mobile-check/check.mjs`.
- Тесты: `auth/PasswordIntegrationTest` (PostgreSQL + GreenMail): хеш в базе, срок,
  одноразовость, неразглашение, лимиты, завершение сессий после сброса и смены, Telegram,
  поведение без SMTP; `seo/SiteSettingsLinkBaseTest`.

### Сессии и перезапуск

Сессии по-прежнему в памяти Tomcat — после деплоя все пользователи выходят (как и раньше).
Реестр сессий тоже в памяти; при одном инстансе этого достаточно.

### Если пользователь не может восстановить пароль сам

Администратор задаёт временный пароль (на сервере, в каталоге окружения):

```bash
# хеш BCrypt: htpasswd уже есть на сервере (basic auth staging/partner)
HASH=$(htpasswd -bnBC 10 "" 'Temp-password-2026' | tr -d ':\n' | sed 's/^\$2y/$2a/')
docker compose exec -T db psql -U rentoptima -d <база> -c \
  "UPDATE users SET password_hash = '$HASH' WHERE lower(email) = lower('host@example.com')"
```

После входа пользователь меняет пароль в «Помощь → Сменить пароль».

## 3. Мягкое подтверждение почты (V38)

### Что сделано

- **V38**: `users.email_verified_at` (когда подтверждён по ссылке), `verify_deadline` (до какого
  момента кабинет работает без подтверждения), `page_needs_verified_email` (страница бронирования
  ждёт подтверждения — только у аккаунтов, созданных после выкладки).
- **Существующие хозяева** (роль OWNER, есть адрес, не `admin`): миграция ставит
  `email_verified = false` и `verify_deadline = момент выкладки + 7 дней`. Для них — только плашка
  и экран через 7 дней; их страницы бронирования и брони через них работают как раньше
  (`page_needs_verified_email = false`). Администратор и пользователи без адреса не затронуты.
  Проверено на базе, поднятой до V37 с «старыми» пользователями.
- **Регистрация**: сразу вход и мастер онбординга, как раньше; письмо «Подтвердите почту для
  OptiRent» со ссылкой `/verify?token=…` (токен `VERIFY` из фазы 2, срок 7 дней, хеш в базе).
- **Плашка** вверху кабинета (`fragments/verify :: banner`): «Подтвердите почту, чтобы не потерять
  доступ», адрес, дата, когда закроется кабинет, «Отправить ещё раз» (не чаще раза в 2 минуты —
  `auth_tokens.created_at`), «Изменить адрес». С фазы 5 первого запуска — полоса в одну строку с ✕
  «скрыть до завтра» (см. `patches/INTEGRATION_FIRST_RUN.md`, раздел 5). Полоса в потоке страницы —
  тур и подсказки не перекрывает; в мастере (`/onboarding`) её нет.
- **Страница бронирования нового неподтверждённого аккаунта** (`EmailVerificationService.pageInactive`):
  - гость на `/b/<slug>` и `/b/<slug>/embed` видит «Страница бронирования скоро заработает»
    (`pages/widget/inactive.html`, noindex); ссылки `/q/`, `/book/`, `/widget/` ведут туда же;
  - `POST /api/widget/<slug>/booking` → 403 `PAGE_INACTIVE` (новый код `WidgetError`); виджет на
    чужом сайте показывает текст ошибки с сервера, пересборка `w.js` не нужна;
  - хозяин, вошедший в кабинет, видит свою страницу как есть и может оставить пробную заявку;
  - в кабинете на страницах виджета — пояснение, кнопки «Копировать» / «Скопировать ссылку» /
    «код встраивания» / «код фрейма» / «текст для гостя» неактивны;
  - в мастере на шаге «Страница готова» вместо ссылки — «Подтвердите почту, и страница заработает»
    + «Отправить письмо ещё раз» (тексты в `onboarding/texts_ru.yml`, `page.ready.verify.*`).
- **Через 7 дней** (`verify_deadline` прошёл) кабинет закрыт экраном `/verify-email`
  (`EmailVerificationInterceptor`): повторное письмо, смена адреса, выход. Публичные страницы,
  `/api/`, статика открыты — страницы бронирования продолжают работать как работали.
- **Смена адреса до подтверждения** (`POST /account/email`, из плашки и с экрана): текущий пароль,
  не больше 3 раз в сутки (счётчик в памяти — после деплоя обнуляется), адрес не занят другим
  аккаунтом (без учёта регистра). Логин меняется вместе с адресом; прежние ссылки гаснут.
- **Ссылка подтверждения** открывается GET-запросом и сразу подтверждает адрес: если почтовый
  сервис проверит ссылку раньше человека, адрес всё равно подтверждён, а человек увидит
  «Почта уже подтверждена». Переход по ссылке сброса пароля тоже подтверждает почту.
- **Без SMTP** ничего из этого не действует: ни плашки, ни экрана, ни закрытой страницы
  (подтвердить адрес нечем).
- Тесты: `auth/EmailVerificationIntegrationTest` (PostgreSQL + GreenMail).

### Что учесть

- Если SMTP включат позже, чем зарегистрировались первые пользователи, у тех, чей срок уже прошёл,
  кабинет закроется сразу — с кнопкой «Отправить письмо». На staging SMTP уже настроен.
- Режимы STRICT / AUTO — раздел 4.

## 4. Режим регистрации и защита регистрации (V39)

### ⚠ До выкладки: проверить дубли логинов и адресов

V39 создаёт уникальные индексы на `lower(username)` и `lower(email)`. Если в базе есть
совпадения без учёта регистра, миграция **останавливается** с их списком в логе
(`V39: логины совпадают без учёта регистра: …`), приложение не стартует, автоматически ничего
не переименовывается. На postgres упавшая миграция откатывается целиком и в историю Flyway не
пишется — после исправления достаточно перезапустить контейнер (`flyway repair` не нужен).
Проверено локально: база до V38 с дублем → понятная ошибка; дубль разведён → V39 прошла.

Проверка на staging и prod до выкладки (в каталоге окружения):

```bash
docker compose exec -T db psql -U rentoptima -d <база> -c "
SELECT 'username' AS what, lower(username) AS value, count(*), string_agg(id::text || ':' || username, ', ') AS users
FROM users GROUP BY lower(username) HAVING count(*) > 1
UNION ALL
SELECT 'email', lower(email), count(*), string_agg(id::text || ':' || email, ', ')
FROM users WHERE email IS NOT NULL GROUP BY lower(email) HAVING count(*) > 1;"
```

Пусто — можно выкладывать. Если есть строки — решить по каждой паре, какой аккаунт настоящий;
лишний, например, отключить и освободить адрес:

```sql
UPDATE users SET active = false, username = username || '.dup-' || id, email = NULL WHERE id = <лишний id>;
```

### Что сделано

- **Режим подтверждения почты** (`RegistrationMode`) — `system_settings` у тенанта администратора:
  `registration_verification` = `SOFT` | `STRICT` | `AUTO` (после выкладки — `AUTO`),
  `registration_auto_threshold` (после выкладки — `100`). Страница настроек хозяина эти ключи
  не показывает (у неё свой список полей).
  - **SOFT** — раздел 3.
  - **STRICT** — после регистрации пользователь вошёл, но кабинет сразу закрыт экраном
    «Проверьте почту» (`verify_deadline` = момент регистрации); после перехода по ссылке —
    мастер онбординга.
  - **AUTO** — SOFT, пока «настоящих» пользователей меньше порога. Настоящий = активный, не
    ADMIN, и (подтвердил почту по ссылке — `email_verified_at` — или в его тенанте есть объект).
    Отключённые, администратор и неподтверждённые без объекта (боты) не считаются. Проверка — при
    каждой регистрации и раз в 15 минут; на пороге настройка сама становится `STRICT`, а
    администратору уходит сообщение в Telegram (бот тенанта администратора, раздел «Интеграции»).
    Чтобы вернуть мягкий режим — выбрать его на странице или поднять порог.
  - Без SMTP режим всегда мягкий и кабинет не закрывается.
- **Страница администратора** `/admin/registration` (роль ADMIN, пункт «Регистрация» в
  «Администрировании»): действующий режим, пользователи всего / настоящих / не подтвердили почту /
  отключены (только числа), переключатель и порог, предупреждение «Почта не настроена».
- **Защита регистрации** (без капчи):
  - скрытое поле-ловушка `company_site` — заполнено → общий отказ «Не получилось
    зарегистрироваться», в лог;
  - подписанный токен времени заполнения формы (`WidgetFormToken`, область `register`): быстрее
    3 секунд — «слишком быстро», старше 12 часов — «открыта слишком долго», без токена или с
    поддельным — общий отказ;
  - не больше 5 попыток регистрации с одного IP в час (после проверки формы; счётчик в памяти);
  - одноразовые домены — `src/main/resources/auth/disposable-domains.txt` (~125 доменов, включая
    formtests.info; поддомены тоже), дополнять там же; отказ понятным текстом. Тот же список
    проверяет смена адреса до подтверждения;
  - пароль — те же правила, что при сбросе (от 10 символов, не совпадает с адресом).
- **Уникальность без учёта регистра**: регистрация проверяет адрес и как логин, и как почту;
  в базе — индексы `ux_users_username_ci`, `ux_users_email_ci`; вход ищет логин без учёта
  регистра. Одновременная регистрация одного адреса — второй получает «уже зарегистрирован».
- После регистрации сессия получает новый идентификатор.
- Тесты: `auth/RegistrationIntegrationTest` (ловушка, время заполнения, лимит IP, одноразовые
  домены, правила пароля, уникальность без учёта регистра в коде и в базе, STRICT, SOFT/AUTO,
  переключение по порогу и кто считается настоящим, Telegram администратору, без SMTP, страница
  администратора и запрет для хозяина).

### Решения, принятые по ходу (для сверки)

- Сброс по ссылке из письма подтверждает почту; ссылка подтверждения подтверждает на GET (защита
  от предпросмотра почтовиков — только для сброса: там GET показывает форму).
- Telegram для сброса — бот тенанта из «Интеграций», не `users.tg_chat_id`.
- STRICT узнаётся по `verify_deadline ≈ created_at` (в пределах часа), отдельной колонки нет.
- Лимиты (`/forgot`, регистрация с IP, смена адреса, неверный текущий пароль) — в памяти процесса,
  обнуляются при деплое; при одном инстансе этого достаточно.
- «Настоящий» пользователь — подтвердил почту **по ссылке** (`email_verified_at`) или создал объект;
  флаг `email_verified` без даты (выставлен до V38) не в счёт.
