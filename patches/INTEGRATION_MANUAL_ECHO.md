# Эхо ручных записей через цепочки каналов (V26)

## Что было

Ручная запись (`channel_id IS NULL`) уходит в iCal-фид всех каналов. Площадка
импортирует её и возвращает в своём фиде — у нас появлялась вторая блокировка
«от канала». Удаление ручной записи её не затрагивало, а удалённая вручную она
возвращалась при следующей синхронизации. Пример на staging: ручная запись id=265
(13–14.11.2026) → RC вернул её с UID 199904867 → блокировка id=267, channel_id=8.

## Что сделано

| Часть | Где |
|---|---|
| UID ручной записи в экспорте: `optirent-manual-<id>@optirent.ru` | `AvailabilityService.buildExportEvents` |
| Пропуск входящих событий с этим префиксом | `ICalChannelAdapter.reconcile` |
| Эвристика по датам (окно 7 дней) для каналов, меняющих UID | `ICalChannelAdapter.reconcile`, `ECHO_MATCH_WINDOW_DAYS` |
| Таблица связей `manual_block_echoes` | V26, `ManualBlockEcho`, `ManualBlockEchoRepository` |
| Мягкое удаление: `calendar_blocks.cancelled_at`, `STATUS:CANCELLED` в экспорте | V26, `GridActionController.delete`, `ICalWriter` |
| Физическое удаление через 30 дней (ежедневно в 04:45) | `ManualBlockRetentionService` |
| Модалка со списком площадок после удаления | `GridActionController.delete`, `fragments/layout.html` |

Anti-echo по `channel_id` в экспорте не менялся.

## Отступления от постановки

- **Маркер и мягкое удаление — для всех ручных записей**, не только `MANUAL_BOOKING`:
  ремонт, личное использование и hold из шахматки эхом возвращаются точно так же.
- **Эвристика по датам работает только при `unit_count = 1`.** В мини-отеле бронь
  другого номера на те же даты — норма, считать её эхом значит занизить занятость.
- **Эхом становится только новое для нас событие.** Блокировка, уже лежащая в базе,
  к ручной записи не привязывается: бронь, пришедшая с площадки раньше, настоящая.
- **Событие с UID-маркером тоже записывается в `manual_block_echoes`** — иначе в
  предупреждении при удалении не было бы площадок, сохраняющих UID.
- **Удалённые записи тоже участвуют в эвристике** (пока им меньше 7 дней): хост
  завёл и через 10 минут удалил, а площадка успела забрать фид.
- **Привязанное эхо со сдвинутыми датами** импортируется как обычная блокировка:
  событие изменили на стороне площадки, это уже не копия нашей записи.
- **Выключатель `APP_ICAL_EXPORT_CANCELLED`** (по умолчанию `true`) — см. риски.
- Мультиюнитные категории (`unit_count > 1`) `STATUS:CANCELLED` не отдают: их
  экспорт — склеенные распроданные ночи без UID отдельных записей.

## Риски, которые надо проверить на пилоте

1. **Площадка не читает `STATUS:CANCELLED`.** Импортёр, который смотрит только на
   DTSTART/DTEND, увидит отменённое событие как занятость и будет держать даты
   закрытыми 30 дней — хуже, чем было (раньше событие просто исчезало из фида).
   Для подстраховки отменённое событие идёт с `TRANSP:TRANSPARENT`. Проверка:
   завести и удалить ручную запись, после опроса фида площадкой посмотреть её
   календарь. Если даты остались закрыты — `APP_ICAL_EXPORT_CANCELLED=false` в
   `.env` (и проброс в `docker-compose.yml`), удаление останется мягким, но в фид
   отменённые не пойдут.
2. **Ложное эхо по датам.** Гость забронировал на площадке, хост увидел уведомление
   и завёл ручную бронь на те же даты раньше, чем наша синхронизация принесла
   блокировку. Событие площадки привяжется как эхо. Пока ручная запись жива, даты
   заняты; если её удалить — у нас даты освободятся, хотя бронь на площадке
   настоящая. Об этом и предупреждает модалка при удалении.
3. **Смена UID при выкладке.** Уже экспортированные ручные записи сменят UID с
   `block-<id>@…` на `optirent-manual-<id>@…`. Площадки, сохраняющие UID, вернут
   новый — он отфильтруется, а старые эхо-блокировки `block-<id>@…` снимутся
   обычной сверкой. Каналы, меняющие UID, могут выдать записи новый свой UID.

## Выкладка на staging

Миграция V26 данные не трогает. Сироты убираются руками, **до** деплоя.

1. Кандидаты в сироты — блокировки каналов, рядом с которыми нет ни ручной записи,
   ни брони на те же даты. Это только список для просмотра: такая блокировка может
   быть и настоящей бронью.

   ```sql
   SELECT cb.id, cb.tenant_id, cb.unit_type_id, cb.channel_id, ch.name AS channel,
          cb.external_uid, cb.from_date, cb.to_date, cb.created_at
   FROM calendar_blocks cb
   JOIN channels ch ON ch.id = cb.channel_id
   WHERE cb.channel_id IS NOT NULL
     AND cb.block_type = 'CHANNEL_SYNC'
     AND NOT EXISTS (
         SELECT 1 FROM calendar_blocks m
         WHERE m.id <> cb.id AND m.unit_type_id = cb.unit_type_id
           AND m.from_date = cb.from_date AND m.to_date = cb.to_date)
     AND NOT EXISTS (
         SELECT 1 FROM bookings b
         WHERE b.unit_type_id = cb.unit_type_id AND b.status = 'BOOKED'
           AND b.check_in = cb.from_date AND b.check_out = cb.to_date)
   ORDER BY cb.from_date;
   ```

2. Для каждой подтверждённой сироты (сейчас известна id=267, RC, UID 199904867):
   сначала удалить бронь **в кабинете площадки** — иначе блокировка вернётся при
   следующей синхронизации, и новая логика её не остановит (ручной записи, к
   которой её можно привязать, уже нет). Затем:

   ```sql
   -- для аудита: что именно удаляем
   SELECT * FROM calendar_blocks WHERE id = 267;
   DELETE FROM calendar_blocks WHERE id = 267 AND channel_id = 8 AND external_uid = '199904867';
   ```

   Если кабинет площадки недоступен — вместо удаления открыть даты в шахматке
   («Открыть даты», `ignored`).

3. Деплой (push в `feat/channels-mvp`), после него hard reload из-за CSRF.

## Проверка после деплоя

- В фиде `/ical/{secret}.ics` ручные записи идут с `UID:optirent-manual-<id>@optirent.ru`.
- Завести ручную бронь, дождаться синхронизации RC: второй блокировки нет, в логе
  `Linked echo from channel 8 (UID=…) to MANUAL block …`, строка в `manual_block_echoes`.
- Удалить её: модалка «Проверьте площадки» со списком каналов; в `calendar_blocks`
  строка с `cancelled_at`; в фиде событие со `STATUS:CANCELLED`; день в шахматке свободен.
- После следующей синхронизации RC блокировка не вернулась (в логе на уровне DEBUG —
  «пропущено известное эхо»).

## Не проверено

Локально прошли только unit-тесты (`mvn -o test`). Flyway V26, шаблон модалки и
поведение реальных площадок со `STATUS:CANCELLED` проверяются только на staging.
