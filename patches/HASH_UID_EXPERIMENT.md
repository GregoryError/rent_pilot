# Хэш-UID для ручных записей в iCal-экспорте — НЕ ПРИМЕНЕНО

**Статус:** эксперимент, в код не вошёл. Полный дифф сохранён рядом:
`patches/hash-uid-experiment.patch` (снят с коммита `4ab0444`).

## Причина, по которой не применено

Гипотеза была: RC (realtycalendar.ru) не импортирует события с UID вида
«имя@домен» (`optirent-manual-271@optirent.ru`), поэтому ручная запись id=271
не закрыла даты в его кабинете. Гипотеза **не подтвердилась**: RC импортировал
эту запись с задержкой. Формат UID ни при чём.

Что это значит на будущее:

- RC закрывает даты не сразу после опроса нашего фида. Отметка в
  `channel_feed_fetches` означает «забрал файл», а не «применил».
  Прежде чем считать, что площадка что-то не импортировала, нужно подождать.
- Ещё до эксперимента было известно, что RC импортировал запись с UID
  `block-265@optirent.ru` — того же вида «имя@домен».

## Что было сделано в эксперименте

Формат UID ручной записи как настройка канала-получателя (а не по названию
площадки: поля `channels.code` нет, все площадки — `ChannelType.ICAL`).

- **Формула:** `MD5("optirent-manual-" + id + "-" + fromDate + "-" + toDate)`,
  32 hex-символа в нижнем регистре, даты в формате ISO (`2026-12-01`).
  Пример входа: `optirent-manual-100-2026-12-01-2026-12-02`.
  Даты входят в ключ, чтобы при их смене площадка видела новое событие.
- **Настройка:** `channels.config_json` → `"manual_uid_format": "HASH"`,
  `Channel.usesHashManualUid()`; переключатель на карточке канала
  (`POST /settings/channels/{id}/manual-uid-format`). Миграции нет.
- **Экспорт:** `ICalFeedController` передаёт флаг в
  `AvailabilityService.exportEvents(..., hashManualUid)`; удалённая запись уходит
  с тем же хэшем, `STATUS:CANCELLED`, `SEQUENCE:1`.
- **Импорт:** `ICalChannelAdapter.reconcile` пропускает событие, чей UID совпал с
  хэшем нашей ручной записи в окне синхронизации (включая удалённые), на любом
  канале. Нужен запрос `CalendarBlockRepository.findHandMadeInRange`.

## Тест-кейсы (все есть в патче)

1. Канал с хэшем: запись id=100, 01–02.12.2026 → UID = MD5 от строки выше.
2. Обычный канал: та же запись → `optirent-manual-100@optirent.ru`.
3. Удалённая запись для канала с хэшем → тот же хэш + `STATUS:CANCELLED` + `SEQUENCE:1`.
4. Смена дат записи меняет хэш.
5. Импорт события с UID = хэш нашей живой записи → пропуск, блокировки нет.
6. То же для удалённой записи → пропуск.
7. Импорт события со случайным хэшем на даты живой записи → тень по датам, как сейчас.
8. `exportEvents` через сервис с моками репозиториев: хэш для канала с флагом,
   обычный UID без него.

## Как восстановить

```bash
git apply --3way patches/hash-uid-experiment.patch
mvn -o test
```

Патч меняет и `CLAUDE.md` (раздел про формат UID) — его текст писался под
неподтверждённую гипотезу, перед применением перечитать. Если код вокруг уйдёт
далеко, `--3way` покажет конфликты; сама логика небольшая и описана выше.

Если хэш когда-нибудь включат на канале, площадка увидит все ручные записи как
новые события: под старым UID они из фида исчезнут.
