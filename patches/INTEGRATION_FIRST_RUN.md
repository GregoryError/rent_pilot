## 0. Изоляция тенантов (до фазы 1)

### Правило

Объект, который загружается по id из адреса или формы, должен принадлежать тенанту вошедшего
пользователя — проверкой `tenant_id` после загрузки или условием `tenant_id` в самом запросе.
**Чужой объект — 404, как несуществующий**, а не 403: по ответу нельзя узнать, что такой id у
кого-то есть. Помощник — `security/Tenancy`:

- `Tenancy.own(repo.findById(id), X::getTenantId)` — загрузить и проверить тенант;
- `Tenancy.found(repo.findByIdAndTenantId…(…))` — для запросов с тенантом в условии;
- `Tenancy.notFound()` — для `UPDATE … WHERE id = ? AND tenant_id = ?`, вернувшего 0 строк.

Своё, но в неподходящем состоянии (заявка уже обработана, запись уже удалена, блокировка не с
площадки) — прежнее сообщение на странице, не 404.

### Что было открыто

Найдено при проходе всех контроллеров и сервисов:

| Где | Что можно было сделать с чужим объектом |
|---|---|
| `POST /pricing/competitors/{id}/delete` | **отключить конкурента другого тенанта** (проверки не было вовсе) |
| `POST /import` | **записать брони и расходы на уборку в чужой объект** — бронь получала тенант объекта, т. е. появлялась в чужой шахматке и выручке |
| `POST /expenses` | привязать свой расход к чужому объекту или чужой статье расходов |
| `CompetitorService.deleteSearch` | без проверки; нигде не вызывался — **удалён** |

Остальные места проверяли тенант, но отвечали по-разному: редирект с «не найдено», молчаливый
успех («Объект обновлён»), 500 на несуществующий id, пустой список — теперь везде 404.

### Тест

`security/TenantIsolationIntegrationTest` (PostgreSQL в контейнере): у пользователей A и B по
полному набору объектов — объект, категория, площадка, блокировка с площадки, ручная запись,
ручная бронь, заявка, страница бронирования, фото, промокод, статья расходов, отзыв,
конкурент, правило AI. A пробует прочитать, изменить и удалить каждый объект B (и подставить
чужой id под свой родительский — своё фото/промокод/категорию под чужой страницей и наоборот):
везде 404, а снимок данных B после всех попыток не изменился. Несуществующий id отвечает так
же, свой объект работает как раньше. На коде до исправления падают все шесть тестов.

### Что учесть

- Устаревшая вкладка с удалённой страницей бронирования или площадкой теперь открывает 404
  вместо редиректа на список с «не найдено».
- Новый эндпоинт с id в адресе или форме — через `Tenancy` и строка в таблице выше.

## 1. Баги первого экрана

### Что сделано

- **«+ Подключить канал» на «Площадках»** без квартиры была неактивной кнопкой без стиля
  неактивности — выглядела рабочей и ничего не делала. Теперь без квартиры в шапке ссылка
  «+ Подключить площадку» в мастер (`/onboarding?step=platforms`; без квартиры мастер сам
  открывает шаг квартиры). Общий стиль `.btn:disabled` в `core.css` — неактивные кнопки
  (например, «Копировать» до подтверждения почты) теперь выглядят неактивными.
- **Дашборд без квартиры** — одно пустое состояние «Здесь будет сводка по квартире» с кнопкой
  «Добавить квартиру» в мастер; метрики, темп, «Требует внимания», рекомендации и переключатель
  месяца не считаются и не показываются. Пропал текст «затем импортируйте бронирования».
- **Темп бронирований** (`BookingStatsService.getBookingPace`) сравнивает занятость следующего
  месяца с нормой, только когда есть с чем сравнивать:
  - норма — среднее занятости по **всем** полным месяцам с первой брони (не больше 12),
    включая месяцы без броней (раньше пустые месяцы выкидывались, и норма завышалась);
  - сравнение — только при **трёх полных месяцах** истории (≥ 90 дней) и ненулевой норме, иначе
    статус `NO_DATA` («Мало данных»), алерта «Загрузка отстаёт» нет. Почему три: норма — среднее
    по месяцам; из одного-двух месяцев она случайна (один удачный месяц — и любой обычный
    выглядит «отставанием»), три месяца — минимум, при котором среднее хоть что-то говорит;
  - раньше при нулевой норме отношение считалось равным 0 → «Отставание» и алерт на пустом
    аккаунте («0.0% vs 0.0%»).
- **Занятость делится на все квартиры**: дни × количество квартир (категории активных объектов с
  их `unit_count`). Раньше — только на дни, и с двумя квартирами получалось до 200%. Так же
  считается «Net RevPAR» (доход минус уборка на ночь в календаре) и занятость в темпе. Без квартир
  — 0, без деления на ноль.
- **«Пустые окна»** (`detectGaps`) ищутся между бронями **одной** квартиры (категории; у старых
  броней без категории — объекта). Раньше брони всех квартир шли одним списком, и бронь второй
  квартиры через день после первой давала ложное «Пустое окно 1 д.» — на дашборде, в календаре
  цен и в рекомендациях автопилота (скидка за «окно»). Автопилот и `/calendar` берут окна только
  своего объекта.
- **Потенциал**: на прошедшем месяце вместо «свободных ночей не осталось» — «месяц прошёл», без
  квартир — «нет квартир в шахматке».
- **/pricing без квартиры** — пустое состояние «Цены появятся вместе с квартирой» с кнопкой в
  мастер вместо «Будни 3000 ₽ / Выходные 4000 ₽» и пустой таблицы. С квартирой: если все
  60 дней заняты — пояснение вместо пустой таблицы; подпись «Обновляется каждый час» заменена
  на правду — «Считаются при открытии страницы».
- **Месяц в заголовке** — именительный падеж (`TextStyle.FULL_STANDALONE`,
  `BookingStatsService.monthName`): «Октябрь 2026». Места, где месяц выводится отдельно от
  числа: переключатель дашборда (было «Октября»), месяц в темпе бронирований (было «NOVEMBER»,
  `Month.toString()`), атрибут `month` в расходах («OCTOBER», в шаблоне не выводился — удалён).
  `/calendar` уже писал «Октябрь» своим массивом. Даты вида «14 октября» и подписи виджета — в
  родительном падеже, как и должны.
- Тренд цен конкурентов: при нулевой прошлой средней сравнение пропускается (было «+Infinity%»).

### Проверено на делении на ноль и пустых величинах

| Где | Было | Стало |
|---|---|---|
| `getBookingPace` | норма 0 → отношение 0 → `BEHIND` | `NO_DATA` |
| `getKpi` occupancy / netRevPar | делитель — дни; с двумя квартирами > 100% | дни × квартиры; 0 квартир → 0 |
| `DashboardForecastService` | делитель `capacityNights`, проверка на 0 есть | без изменений |
| `ChannelDiagnosticsService.median` | пустой список → null | без изменений |
| `PricingEngine.applyCompetitorGravity` | `market <= 0` → без изменения цены | без изменений |
| `CompetitorService` тренды | `prevAvg = 0` → `Infinity` | пропуск |
| `DashboardController.pct` | `max = 0` → 0 | без изменений |
| `AlertSchedulerService`, `ConflictDetector` | делений нет | — |

### Что учесть

- Темп по-прежнему грубый: уже набранная занятость следующего месяца сравнивается с полной
  занятостью прошлых. Честное сравнение — «сколько было забронировано на прошлые месяцы за
  столько же дней до начала», для этого нужна дата создания брони у всех источников. Пока
  предупреждение срабатывает чаще, чем следовало бы, — в начале месяца следующий почти всегда
  «отстаёт».
- Брони с площадок по iCal — это блокировки, а не брони: в «Факт по броням» и темп они не
  попадают (так было и раньше). Шахматка, «Занятость» и «Прогноз» вверху дашборда их учитывают.

### Тесты

- `service/BookingStatsServiceTest` — темп без броней и с короткой историей (`NO_DATA`, без
  алерта), норма с пустыми месяцами, две квартиры (50%/100%), без квартир (без деления на ноль),
  окна внутри одной квартиры, «Октябрь»/«Май»/«Ноябрь».
- `FirstRunIntegrationTest` — пустой дашборд (нет метрик и алертов, кнопка в мастер), дашборд с
  квартирой без истории («Октябрь 2026», «Мало данных»), пустой /pricing, ссылка «Подключить
  площадку» в мастер.

## 2. Один источник цены — цена квартиры

### Как было

| Где | Откуда брали цену |
|---|---|
| Шахматка, дашборд, страница бронирования, сумма для гостя (`EffectivePriceService`) | цена квартиры: плановая на дату → `unit_types.weekend_price` → `unit_types.base_price` |
| Автопилот и рекомендации на /pricing (`PricingEngine`) | **настройки тенанта** `weekday_base_price` / `weekend_base_price` |
| Ценовой календарь `/calendar` | **настройки тенанта** |
| AI-советник цен (`AiPricingAdvisor`), AI-чат (`AiChatService`) | **настройки тенанта**; город — настройка `city` или зашитый «Выборг» |

Мастер записывает цену в квартиру, а рекомендации считались от 3000/4000 из настроек, которые
регистрация записывала каждому. Выходные тоже различались: автопилот считал выходными ночи пт,
сб и вс, шахматка и виджет — сб и вс.

### Как стало

- **Цена дня — одна**: `EffectivePriceService` (плановая цена на дату → цена выходных → цена в
  будни) для шахматки, дашборда, страницы бронирования, автопилота, `/calendar`, AI-советника и
  AI-чата. Квартира объекта для рекомендаций — первая действующая категория
  (`PricingEngine.pricedUnit`); если категорий несколько, на /pricing подписано, по какой
  считается. Колонка «База» в рекомендациях — та же цена, что в шахматке.
- Праздники: база — цена квартиры на этот день; праздничная надбавка, как и раньше, — множителем
  `ProductionCalendarService` (прежде к ней добавлялась ещё и подмена базы на «выходную»).
- У квартиры нет цены — рекомендаций нет, /pricing: «У квартиры не задана цена за ночь» со
  ссылкой на «Объекты»; `/calendar` вместо «0 ₽» не показывает цену.
- **Выходные — ночи с пятницы и с субботы** (`EffectivePriceService.isWeekend`, дата — день
  заезда). Одно правило везде, включая журнал решений автопилота.
- **Пределы мин./макс. цены**: новым аккаунтам не записываются (пусто); пустой предел — 50% и
  250% цены квартиры на день (`PricingEngine.bounds`). У существующих аккаунтов значения
  остались; если цена квартиры выходит за них — предупреждение на /pricing со ссылкой в настройки.
- **Настройки `weekday_base_price`, `weekend_base_price`, `city`** — теперь «значения по
  умолчанию для новых квартир» (`ApartmentDefaults`): только подсказка (placeholder) в полях цены
  и города в мастере и в форме «Объекты». Пустые — подсказки нет. Регистрация заводит эти ключи и
  пределы пустыми. В форме объекта больше нет зашитого «Выборг», AI-советник и AI-чат берут
  город квартиры. Перенос этих полей в «Продвинутые» — фаза 4.

### ⚠ Цена выходных сместилась на день

У квартир с заданной `weekend_price` после выкладки:

- ночь **с пятницы на субботу** стала стоить как выходная (была — как будни);
- ночь **с воскресенья на понедельник** стала стоить как будни (была — как выходная).

Это касается шахматки, прогноза на дашборде и **суммы для гостя на странице бронирования** —
для новых расчётов. Уже созданные заявки и брони хранят свою сумму и не меняются. Плановые цены
на конкретные даты (`planned_prices`) не затронуты.

Кого коснётся — до выкладки (в каталоге окружения):

```bash
docker compose exec -T db psql -U rentoptima -d <база> -c "
SELECT t.name AS tenant, p.name AS property, ut.name AS unit, ut.base_price, ut.weekend_price,
       (SELECT count(*) FROM booking_widgets w WHERE w.unit_type_id = ut.id AND w.active) AS pages
FROM unit_types ut
JOIN properties p ON p.id = ut.property_id AND p.active
JOIN tenants t ON t.id = ut.tenant_id
WHERE ut.active AND ut.weekend_price IS NOT NULL AND ut.weekend_price <> ut.base_price
ORDER BY t.name;"
```

Хозяевам из списка со страницей бронирования стоит сказать заранее: «цена выходных теперь
действует для ночей с пятницы и с субботы, ночь на понедельник — по будней цене».

Чьи пределы мешают рекомендациям (те же аккаунты увидят предупреждение на /pricing):

```bash
docker compose exec -T db psql -U rentoptima -d <база> -c "
SELECT t.name, ut.base_price, ut.weekend_price, lo.value AS min_price, hi.value AS max_price
FROM unit_types ut
JOIN tenants t ON t.id = ut.tenant_id
LEFT JOIN system_settings lo ON lo.tenant_id = ut.tenant_id AND lo.key = 'min_price_floor'
LEFT JOIN system_settings hi ON hi.tenant_id = ut.tenant_id AND hi.key = 'max_price_ceiling'
WHERE ut.active AND ut.base_price IS NOT NULL
  AND ((hi.value ~ '^[0-9]+$' AND greatest(ut.base_price, coalesce(ut.weekend_price, 0)) > hi.value::int)
    OR (lo.value ~ '^[0-9]+$' AND least(ut.base_price, coalesce(ut.weekend_price, ut.base_price)) < lo.value::int));"
```

### Тесты

- `service/EffectivePriceServiceTest` — ночи пт и сб выходные, вс — будни.
